# Publishing after maintainer review

The initial extraction performed no publication. Following maintainer approval, the source and model-v1/v0.1.0 GitHub releases were published on 2026-11-01; see [publication verification](PUBLICATION-2026-11-01.md). Registry publication remains separate.

1. Review the engine/model notices and the qualified v1 provenance. Set the single `REPOSITORY_OWNER` constant in `core/qrk-onnx/src/lib.rs`; no other binding keeps a second owner setting.
2. Publish each pinned model under its separate model release (current: `model-v2`) with `model/model-manifest.json` and all attribution. The source loader repeats SHA-256 + exact-size validation even if a caller supplies a modified manifest. The clean v2 workflow passed source fidelity, native acceptance/retry gates and local owned-recording checks; v0.2.0 promotes its pinned hash. Older v1 remains separately available. See [export status](../model/export/STATUS-2026-11-01.md).
3. Run the desktop/Apple CI. Actual Windows/Linux/Intel execution is required before claiming those runners passed. The local Windows check is compile-only. Hardware-microphone accuracy remains separate from silence and direct-file tests.
4. Build/review release archives. `tools/build_xcframework.py` produces an ignored Apple archive; `tools/package_swift.py` zips it. The remote SwiftPM checksum must refer to the **exact reviewed archive**: run `tools/package_swift.py --pin --archive PATH_TO_REVIEWED_ZIP --tag v0.1.0`, commit the metadata, and publish that same zip. Do not rebuild and upload different bytes under that checksum. The root Swift Package and `bindings/swift` package use the same metadata file. Local source builds use the ignored local XCFramework instead.
5. `release.yml` collects four CLI/C archives, four Node prebuild archives, Python abi3 wheels and an Apple XCFramework. Its aggregate job packs NuGet only after all four native RID assets exist. It attaches files to a **draft** GitHub release. Review/pin the exact Swift checksum before publishing; do not replace an already pinned Swift asset with a later CI rebuild. This workflow does not publish to npm, PyPI or NuGet.
6. Assemble Node prebuilds into the Node package (`npm pack`), wheel(s) for Python 3.9+, and the aggregate NuGet. Keep notices included. Windows consumers may need Microsoft's VC++ Redistributable. Native Linux builds target the runner's glibc baseline (Ubuntu 22.04+); older glibc wheels need a manylinux builder, not a renamed tag.
7. Sign/notarize desktop distributions where the host application requires it; the SDK does not disable Gatekeeper, request broad entitlements, or install a service.

Swift users can then add the public repository as one SwiftPM dependency and choose the engine/audio product. The v0.1.0 archive is already pinned. Before a future reviewed release is pinned, source checkouts first run the Apple build tool; this deliberate gate prevents an invented download URL or checksum.

The release preflight verifies/reuses an already pinned archive instead of rebuilding and overwriting it. For the initial release, the still-unpublished v0.1.0 tag was moved to the checksum-pin commit before publication so version-based SwiftPM dependencies contain the working manifest. CI uses supported macos-15 arm64/macOS-15-intel runners; macOS 14 is in retirement brownout. Documentation-only changes do not trigger another full native build.

SwiftPM version resolution evaluates manifests without a normal source checkout. Do not read sidecar metadata through `#filePath` inside Package.swift. The archive URL/checksum must be inline; `package_swift.py --pin` updates both manifests and binary-release.json together. Context.packageDirectory is used only to discover an optional local development archive. `check_swift_dependency.py` tests a tagged bare-Git dependency in CI. Source-only patch tags may reuse a previously published archive; release preflight verifies that exact older asset and avoids overwriting it. v0.1.1 is the initial manifest-only patch; native binaries remain v0.1.0.

Archive reuse across different tags requires an explicit `source_only_releases` allowlist in binary-release.json. Other future tags rebuild by default; do not silently reuse an older binary for a native-code release.

For a release that adds C ABI symbols, do not expose a new semantic-version tag while its manifest still points to the previous archive. Dispatch `release.yml` on a feature branch with `release_tag` set to the intended version and `build_only=true`. This builds the same platform archives and aggregate NuGet package as the normal release workflow, but creates neither a release nor a tag. Download/review the workflow artifacts and pin the exact Apple ZIP with `package_swift.py --pin` before committing the final manifest.

Stage those exact reviewed files in a draft under a non-semantic tag such as `staging-spot-v0.3.0`, targeting the checksum-pin commit. Once the assets and all platform gates pass, change the draft's tag to the intended semantic version and publish it in the same release edit. Confirm the public tag targets the pin commit, then fast-forward `main`. Run the strict tagged SwiftPM consumer again against the now-public archive. Record both the artifact-build SHA and final manifest SHA; do not rebuild an already pinned ZIP merely to make their SHAs identical. This avoids a public package version temporarily linking new Swift wrappers to an older C ABI.
